## Critical Security Constraints (from PITFALLS.md)

**Pitfall 1 — JWT in localStorage:** Access tokens MUST be stored in React state only, never localStorage. Refresh tokens in HttpOnly cookies only. This plan establishes the JWT service that creates these tokens.

**Pitfall 2 — Refresh race condition:** Prevented by axios interceptor semaphore (planned in Wave 4). This plan provides the `/api/auth/refresh` route that the interceptor will call.

**Pitfall 3 — CORS wildcard breaks credentials:** Current `cors()` call in `index.ts` uses wildcard origin. **THIS MUST BE FIXED FIRST** before any auth code. The current code is explicitly mentioned in PITFALLS.md as blocking authenticated requests.

## Backend File Patterns

Backend imports MUST use `.js` extensions (e.g., `import config from './config/env.js'`). TypeScript transpiles `.ts` → `.js`; Node ESM requires explicit extensions.

## Type Safety

All auth types must be strict: no `any`, no loose string unions. JWT payload, user records, and refresh token records use explicit interfaces defined in `backend/src/types/auth.ts`.

  <name>Task 4: Create password hashing service (bcrypt wrapper)</name>
  <files>backend/src/services/passwordService.ts</files>
  <action>
    Create `backend/src/services/passwordService.ts` with two async functions for password operations.
    
    **Requirements:**
    - hashPassword(password: string): Promise<string>
      - Hash input password using bcrypt.hash with cost 12 (per STACK.md requirement)
      - Return the hash string
      - Throw error if password is falsy or cost 12 fails
    - verifyPassword(password: string, hash: string): Promise<boolean>
      - Compare input password against stored hash using bcrypt.compare
      - Return true/false (not throw)
      - Handle errors gracefully (return false on error, not throw)
    
    **Constraints:**
    - Cost factor MUST be 12 (not 10, not 11, not 13 — per STACK.md)
    - Use native `bcrypt` package (not bcryptjs) per STACK.md
    - Use `.js` extensions on imports (e.g., `import { types } from '../types/auth.js'` — though this file only imports bcrypt)
    - Add JSDoc comments (optional but recommended per CLAUDE.md)
    
    **File format:**
    ```typescript
    // backend/src/services/passwordService.ts
    import bcrypt from 'bcrypt'
    
    const BCRYPT_COST = 12
    
    export async function hashPassword(password: string): Promise<string> {
      if (!password) {
        throw new Error('Password cannot be empty')
      }
      const hash = await bcrypt.hash(password, BCRYPT_COST)
      return hash
    }
    
    export async function verifyPassword(password: string, hash: string): Promise<boolean> {
      try {
        const isValid = await bcrypt.compare(password, hash)
        return isValid
      } catch (error) {
        console.error('Password verification error:', error)
        return false
      }
    }
    ```
    
    **Why this pattern:**
    - Cost 12 = ~250ms on modern hardware (acceptable for login/signup)
    - Error handling in verify: return false rather than throw so callers don't need try-catch for normal failure
    - Both functions async (bcrypt.hash and bcrypt.compare use event loop, not threads)
  </action>

  <files>backend/src/services/jwtService.ts</files>
  <action>
    Create `backend/src/services/jwtService.ts` with four async functions for JWT operations. This service creates both access and refresh tokens, and verifies both.
    
    **Requirements:**
    - signAccessToken(payload: JWTPayload): Promise<string>
      - Sign access token with JWT_SECRET from config
      - Expiration: 15 minutes (per requirements: "15min access token")
      - Payload: userId, email, tier (NO passwords, NO sensitive fields)
      - Return signed token string
    - signRefreshToken(payload: JWTPayload): Promise<string>
      - Sign refresh token with JWT_REFRESH_SECRET from config
      - Expiration: 7 days (per requirements: "7d refresh token")
      - Payload: userId, email, tier (same as access token)
      - Return signed token string
    - verifyAccessToken(token: string): Promise<JWTPayload | null>
      - Verify token against JWT_SECRET
      - Return decoded payload if valid, null if invalid/expired
      - Catch verification errors and return null (don't throw)
    - verifyRefreshToken(token: string): Promise<JWTPayload | null>
      - Verify token against JWT_REFRESH_SECRET
      - Return decoded payload if valid, null if invalid/expired
      - Catch verification errors and return null
    
    **Imports and config:**
    - Import jsonwebtoken: `import jwt from 'jsonwebtoken'`
    - Import config: `import config from '../config/env.js'`
    - Import JWTPayload type: `import type { JWTPayload } from '../types/auth.js'`
    - Use `.js` extensions per backend ESM requirement
    
    **File format (pseudocode):**
    ```typescript
    import jwt from 'jsonwebtoken'
    import config from '../config/env.js'
    import type { JWTPayload } from '../types/auth.js'
    
    export async function signAccessToken(payload: JWTPayload): Promise<string> {
      const token = jwt.sign(payload, config.jwtSecret, {
        expiresIn: '15m',
        algorithm: 'HS256',
      })
      return token
    }
    
    export async function signRefreshToken(payload: JWTPayload): Promise<string> {
      const token = jwt.sign(payload, config.jwtRefreshSecret, {
        expiresIn: '7d',
        algorithm: 'HS256',
      })
      return token
    }
    
    export async function verifyAccessToken(token: string): Promise<JWTPayload | null> {
      try {
        const decoded = jwt.verify(token, config.jwtSecret, {
          algorithms: ['HS256'],
        })
        return decoded as JWTPayload
      } catch (error) {
        return null
      }
    }
    
    export async function verifyRefreshToken(token: string): Promise<JWTPayload | null> {
      try {
        const decoded = jwt.verify(token, config.jwtRefreshSecret, {
          algorithms: ['HS256'],
        })
        return decoded as JWTPayload
      } catch (error) {
        return null
      }
    }
    ```
    
    **Why these patterns:**
    - 15m access token: short-lived, minimizes exposure if stolen
    - 7d refresh token: long-lived, rotated on each use (wave 3 implements rotation logic)
    - Both use separate secrets (prevents old refresh token from being used as access token if signing key leaked)
    - HS256 is industry standard for JWT
    - Verify functions return null instead of throwing (cleaner error handling in routes)
    - No database access here (verify functions only check JWT signature, not database revocation; database check happens in routes)

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → API | Untrusted HTTP requests; passwords, tokens in request body/headers |
| Browser → LocalStorage | XSS attacker can read localStorage; mitigated by storing tokens in memory/cookies only |
| Browser → HttpOnly Cookie | XSS attacker cannot read HttpOnly cookies; protected by secure/SameSite flags |
| API → Database | Trusted internal; tokens/hashes passed via driver |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Spoofing | JWT claims | mitigate | Verify JWT signature with secret in jwtService.verifyAccessToken; secret loaded from env only |
| T-06-02 | Tampering | Password hash | mitigate | Use bcrypt with cost 12 (salting + hashing); passwordService.hashPassword enforces cost factor |
| T-06-03 | Repudiation | Login audit | accept | Not required for v1; audit logging deferred to Phase 6b |
| T-06-04 | Information Disclosure | JWT in localStorage | mitigate | Per PITFALLS.md, store access tokens in memory only (Wave 4 task enforces); refresh tokens in HttpOnly cookies |
| T-06-05 | Information Disclosure | JWT payload | mitigate | JWTPayload interface explicitly defines claims (userId, email, tier); passwordHash never included in token |
| T-06-06 | DoS | Refresh token rotation | mitigate | Per PITFALLS.md Pitfall 2, axios interceptor implements semaphore (Wave 4); this plan provides stateless verify function |
| T-06-07 | Elevation of Privilege | Tier spoofing | mitigate | Tier claim verified by server-side JWT signature; frontend cannot forge 'pro' tier |
